URL shortener in Go — how it is put together

The entry the list points to is “Let’s build a URL shortener in Go — with Gin & Redis” by Eddy WM, a four-part build. It is a small service with a clean split: an HTTP layer, a pure code generator, and a Redis-backed store. Below is the design those four parts assemble.

Go 1.13 Gin 1.6 go-redis v8 SHA-256 → Base58 :9808 Redis only · 6 h TTL
01

Request topology

Two routes do all the work. One writes a mapping, one reads it back and redirects.

Write — create a short link
1

Client sends POST /create-short-url with { long_url, user_id }.

2

Gin routes to CreateShortUrl; ShouldBindJSON validates both fields.

3

Generator turns the pair into an 8-character code. Pure, deterministic, no datastore.

4

Store receives the mapping. Note that user_id is passed in but never persisted.

5

Redis holds code → long_url with a fixed 6-hour expiry.

Read — follow a short link
6

Client opens GET /<code> — the same host, no separate redirect domain.

7

Gin routes to HandleShortUrlRedirect, which reads the path parameter.

8

Store looks up the code. A miss returns an error that is turned into a panic.

9

Redis returns the original URL; the handler answers 302 and the browser follows it.

Solid boxes are Go packages. main.go is the only place routes are registered. Source: eddywm/go-shortener-wm
02

How a URL becomes eight characters

The generator is the whole algorithm: hash, narrow to 64 bits, encode, truncate.

Why Base58: it drops 0 O I l, so codes survive fonts, screenshots and double-clicks. Sandwiched between the hash and the prefix: finalString[:8]
03

What is actually stored, and through what interface

The data model is a single Redis key. The API surface is three functions.

The record

One key per generated code. Nothing else is written.

KEYjTa4L57P
VALUEhttps://www.guru3d.com/news-story/…
TTL6h 00m 00s
USERnot stored

No user_id, no created_at, no hit counter. Because the code is derived from url + user_id, the same pair can never produce a second link — and an existing one can’t be listed or revoked.

The interface

Three exported functions connect the three packages.

shortener.GenerateShortLink(initialLink, userId string) string
pure; used only on the write path
store.SaveUrlMapping(shortUrl, originalUrl, userId string)
no return value — it panics on failure
store.RetrieveInitialUrl(shortUrl string) string
panics on a cache miss, so “unknown” becomes a 500

Package map

About 200 lines of Go, test files included.

go-shortener-wm/
├─ main.go                      # gin.Default(), 3 routes, store boot, :9808
├─ handler/
│  └─ handlers.go              # HTTP in/out: bind JSON, read param, 302 out
├─ shortener/
│  ├─ shorturl_generator.go    # pure code generation: sha256 + base58
│  └─ shorturl_generator_test.go
└─ store/
   ├─ store_service.go         # redis.Client wrapper, package-level singleton
   └─ store_service_test.go
Reading order
  1. main.go registers three routes, then boots the store before r.Run.
  2. handler parses HTTP and delegates; it holds no logic of its own.
  3. shortener is pure, so its test needs no Redis at all.
  4. store is the only package that knows Redis exists.
04

Where the design holds, and where it doesn’t

Read as a tutorial, this is a clean separation of concerns. Read as a service, five things would bite you in production.

Codes are deterministic, and never checked

sha256(url + user_id) means forever the same code for the same pair. Nothing verifies whether that 8-char slice already belongs to another URL, so a collision silently overwrites the old mapping.

Every link expires in 6 hours

The 6-hour CacheDuration is used as the Redis TTL, which is right for a cache and wrong for a link. When it lapses, the next visit panics rather than returning a 404 page.

Redis is the only store

The article says it plainly: real traffic needs Postgres or MySQL for cold values with Redis in front. That tier appears only in the “next steps” list, not in the code.

Errors are panics

SaveUrlMapping and RetrieveInitialUrl panic on any Redis error. Gin’s recovery middleware turns that into a 500, so a typo’d short code looks like a server fault.

The response host is hardcoded

host := "http://localhost:9808/" is concatenated into every response, so the service returns unusable links anywhere except a laptop.

What is genuinely good

The generator is pure and independently testable, storage sits behind one narrow interface, and Base58 is a thoughtful choice for something humans read and retype.
